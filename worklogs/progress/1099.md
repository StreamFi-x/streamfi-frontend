# Issue #1099: Channel Points Balance

## Branch: feat/channel-points-system
## Status: In Progress

## Implementation Plan

### Overview
Viewer earns and spends channel points (per-creator loyalty currency) with balance management and transaction tracking.

### Requirements
1. **GET** `?viewer_id&creator_id` - Returns `{ balance, lifetime_earned }`
2. **POST /grant** `{ viewer_id, creator_id, amount, reason }` - Increments balance
3. **POST /spend** `{ viewer_id, creator_id, amount, item }` - Decrements balance with insufficient-balance check
4. Tests cover grant, spend, and overdraw rejection scenarios

### Scope Constraints
- All files must live inside `app/api/routes-f/`
- No modifications, imports from, or additions to `lib/`, `utils/`, `types/`, `components/`, or anywhere outside `app/api/routes-f/`

### Data Models
```typescript
interface ChannelPointsBalance {
  viewer_id: string;
  creator_id: string;
  balance: number;          // Current available points
  lifetime_earned: number;  // Total points ever earned
  updated_at: Date;
}

interface Transaction {
  id: string;
  viewer_id: string;
  creator_id: string;
  type: 'grant' | 'spend';
  amount: number;
  reason?: string;          // For grants: 'watch', 'tip', 'subscription', etc.
  item_id?: string;         // For spends: catalog item ID
  timestamp: Date;
}

interface BalanceResponse {
  balance: number;
  lifetime_earned: number;
}

interface GrantRequest {
  viewer_id: string;
  creator_id: string;
  amount: number;
  reason: string;
}

interface SpendRequest {
  viewer_id: string;
  creator_id: string;
  amount: number;
  item: string;  // Catalog item ID or description
}
```

### Validation Rules
1. `viewer_id`: Required, valid user ID format
2. `creator_id`: Required, valid user ID format
3. `amount`: Required, positive integer, min 1, max 1000000
4. `reason`: Required for grants, max 200 characters
5. `item`: Required for spends, max 100 characters
6. Balance must be sufficient for spend operations

### Business Logic
1. **GET Balance**: Retrieve or initialize (0 balance) for viewer-creator pair
2. **Grant Points**: Increment both balance and lifetime_earned, log transaction
3. **Spend Points**: Check sufficient balance, decrement balance, log transaction
4. **Overdraw Prevention**: Reject spend requests that would result in negative balance

### Test Coverage Requirements
- ✓ GET returns zero balance for new viewer-creator pair
- ✓ GET returns correct balance for existing pair
- ✓ POST /grant increases balance and lifetime_earned
- ✓ POST /spend decreases balance when sufficient funds
- ✓ POST /spend rejects when insufficient balance
- ✓ Transaction history is logged for both grant and spend
- ✓ Validation rejects invalid inputs
- ✓ Concurrent spend requests are handled correctly
