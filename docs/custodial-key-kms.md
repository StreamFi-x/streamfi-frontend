# Custodial key encryption with AWS KMS (#1396)

`users.encrypted_stellar_key` holds custodial users' Stellar secret keys.
Previously every key was AES-256-GCM encrypted under one static key
(`STELLAR_ENCRYPTION_KEY`), so leaking that one variable exposed every
wallet. Keys are now protected by **envelope encryption under AWS KMS**.

Code: `lib/custodial-keys/` (`index.ts` envelope, `kms.ts` KMS adapter,
`legacy.ts` read-only legacy format, `migration.ts`),
`scripts/migrate-custodial-keys-to-kms.ts`.

## Why AWS KMS

StreamFi runs on Vercel, whose functions run on AWS, and has no existing
KMS/Vault dependency. AWS KMS is the lowest-latency managed option from that
runtime. Keys stay in FIPS 140-3 validated HSMs, and every call is logged in
CloudTrail. The adapter is one small interface (`KeyManagementService`), so
another provider could be added later.

## Key hierarchy and envelope

```
KEK  (AWS KMS key, never leaves KMS)
 └─ DEK  (random 256-bit, one per wallet, generated by KMS GenerateDataKey)
     └─ Stellar secret  (AES-256-GCM, 96-bit IV, 128-bit tag)
```

Stored value — explicitly versioned, never classified by guessing at its
shape:

```
ckv2:<base64url(JSON)>
{ "v": 2, "alg": "AES-256-GCM", "kms": "aws-kms",
  "kid": "<KMS key ARN>", "edk": "<wrapped DEK>",
  "iv": "…", "tag": "…", "ct": "…" }
```

- **One DEK per wallet**: a compromised DEK exposes exactly one wallet, and
  the application never holds a key that can decrypt more than one.
- The user id is bound twice: in the GCM AAD and in the KMS encryption
  context `{purpose: "streamfi-custodial-stellar-key", user_id}`. An
  envelope copied onto another user's row does not decrypt.
- `Decrypt` is pinned to the envelope's `kid`, so KMS refuses to unwrap
  under any other key.
- Plaintext DEKs are zeroed immediately after use. The secret itself is a JS
  string and cannot be zeroed; it is never logged, persisted or included in
  errors.

## Code paths

| Path                               | Behaviour                                                                                 |
| ---------------------------------- | ----------------------------------------------------------------------------------------- |
| `POST /api/auth/onboarding`        | new wallets are enveloped at creation                                                     |
| `POST /api/auth/regenerate-wallet` | new envelope; clears any stale legacy backup                                              |
| `POST /api/auth/export-key`        | KMS-mediated decrypt (legacy rows readable only while the legacy key is still configured) |

There are no other readers or writers of `encrypted_stellar_key` (no server-side signing path exists today).

**No insecure fallback**: a KMS failure is never answered by trying the
static key. Timeouts and throttling return `503` (`Retry-After: 30` on
export); access denied, disabled key or bad ciphertext return a generic
`500`. Errors carry a code, never key material.

KMS calls: 2 s connect / 5 s request timeout, 3 attempts with SDK backoff.
KMS is now a hard dependency for creating and exporting custodial wallets.

## Configuration

| Variable                   | Purpose                                                                          |
| -------------------------- | -------------------------------------------------------------------------------- |
| `CUSTODIAL_KEY_KMS_KEY_ID` | KMS key ARN or alias ARN (required)                                              |
| `CUSTODIAL_KEY_KMS_REGION` | defaults to `AWS_REGION`                                                         |
| AWS credentials            | standard provider chain (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, or a role) |
| `STELLAR_ENCRYPTION_KEY`   | legacy key — **only** until the migration is complete (see below)                |

## IAM (least privilege)

Key: symmetric `SYMMETRIC_DEFAULT`, automatic rotation enabled (rotation
keeps old key material, so existing envelopes keep decrypting).

Application role (Vercel runtime) — nothing else:

```json
{
  "Effect": "Allow",
  "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
  "Resource": "arn:aws:kms:<region>:<account>:key/<key-id>",
  "Condition": {
    "StringEquals": {
      "kms:EncryptionContext:purpose": "streamfi-custodial-stellar-key"
    }
  }
}
```

Migration operator role: the same statement, used only while running the
migration CLI. Key administration (`kms:Create*`, `kms:Put*`,
`kms:ScheduleKeyDeletion`, `kms:DisableKey`, …) belongs to a separate admin
role in the key policy — never the application. Prefer short-lived
credentials (IAM role / OIDC federation) over long-lived access keys.

## Auditability

CloudTrail records every `GenerateDataKey` and `Decrypt` with the KMS key,
the calling principal, the time, and the encryption context — including the
`user_id` whose wallet was decrypted. Application logs add
`custodial_key_kms_encrypt` / `custodial_key_kms_decrypt` (user id + key ARN
only) and `custodial_key_legacy_decrypt` while legacy rows remain.

## Rollout, migration and retirement

1. **Apply** `db/migrations/20260925100000_custodial_key_kms.sql`, create the KMS
   key and IAM role, set `CUSTODIAL_KEY_KMS_KEY_ID`. Deploy. From now on
   every new or regenerated wallet is enveloped; legacy rows remain readable.
2. **Dry run** (writes nothing, exercises KMS round trips):
   `npm run migrate:custodial-keys -- --dry-run`
3. **Migrate**: `npm run migrate:custodial-keys -- --migrate`
   For each legacy row: decrypt with the legacy key → check that the key's
   public key equals `users.wallet` → envelope with a fresh DEK → decrypt it
   back through KMS and compare → conditional `UPDATE` (only if the row is
   unchanged) that stores the envelope and keeps the old ciphertext in
   `encrypted_stellar_key_legacy` → audit event in
   `custodial_key_migration_events`.
   - **Resumable / idempotent**: rows are selected by the absence of the
     `ckv2:` prefix; rerunning after any interruption continues where it
     stopped and never touches migrated rows.
   - **Failures** (KMS error, verification mismatch, undecryptable legacy
     row, wallet mismatch) leave the row untouched, are audited with a reason,
     are listed in the CLI output, and raise an alert. Rerun to retry.
   - `wallet_mismatch` rows hold a key that does not control the user's
     current wallet (e.g. the wallet was changed after onboarding). Review
     them, then migrate with `--accept-wallet-mismatch` (key carried over
     bit-for-bit).
4. **Verify**: `npm run migrate:custodial-keys -- --verify`. It re-decrypts
   every envelope through KMS and checks it against the wallet and the legacy
   backup.
5. **Purge legacy backups**:
   `npm run migrate:custodial-keys -- --purge-legacy --confirm`. It refuses
   to run while any legacy row remains, and re-verifies each row before
   nulling its backup.
6. **Retire the static key**. First set `TWO_FA_ENCRYPTION_KEY` to the
   current `STELLAR_ENCRYPTION_KEY` value: the 2FA module
   (`routes-f/2fa/_lib/totp.ts`) falls back to `STELLAR_ENCRYPTION_KEY`, and
   removing it without this would break existing 2FA secrets. After that
   value no longer decrypts any custodial ciphertext, remove
   `STELLAR_ENCRYPTION_KEY` from every environment. Any stray legacy row now
   fails closed (`LEGACY_KEY_UNAVAILABLE`).

**Rollback**: until step 5, every migrated row still has its legacy
ciphertext in `encrypted_stellar_key_legacy`, so a row can be restored with
`UPDATE users SET encrypted_stellar_key = encrypted_stellar_key_legacy`.
Never schedule deletion of the KMS key while any `ckv2:` row exists; use
disable (reversible) for emergency revocation.

The CLI prints identifiers, outcomes and reasons only. It never writes key
material to logs, files or the audit table.
